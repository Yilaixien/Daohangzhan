# 优化链接管理中死链检测流程

## 概述 Summary

优化「链接管理 → 死链检测」全流程，覆盖三个方面：
1. **结果展示与操作**：把现在的 `alert()` 计数弹窗改为结果明细弹窗，逐条列出每个链接的检测状态（HTTP 状态码 / 无法访问），并支持对失效链接单独「隐藏」「删除」及「一键隐藏全部失效」。
2. **性能与稳健**：把串行逐个 `HEAD` 请求改为带并发上限的检测（默认同时 5 个），`HEAD` 失败/被拒时自动回退 `GET`，减少误判和整体耗时。
3. **修复 Supabase 检测失效**：Supabase 模式下当前 `mode:'no-cors'` 导致 `resp.status` 恒为 0、所有链接都被判死。改为以「请求是否成功建立」判定可达性，正确区分死链/存活。

## 拟改动 Proposed Changes

采用「REST 后端为主、Supabase 同步兼容」：后端提供完整 http 状态检测；前端服务层做并发 + 回退；Supabase 模式以可达性兜底。**保持契约签名不变**（`{id,status}[]`），前端页面用本地已加载的 `links`（含 `title`/`url`）来补全展示信息，避免扩大契约改动面。

### 1. 后端 REST：并发 + HEAD→GET 回退
**文件**：`backend-reference/src/routes/links.js`（`/check-dead` 路由）

- 抽出两个私有工具函数（放文件顶部或路由内）：
  ```js
  // 单链接检测：HEAD 优先，被拒/异常时回退 GET（Range: bytes=0-0），返回 http 状态码，不可达返回 0
  async function detectUrl(url, timeoutMs) { ... }
  // 并发执行器：把链接列表按 limit 分批，控制同时在途请求数
  async function runWithConcurrency(items, limit, worker) { ... }
  ```
- `detectUrl(url, timeoutMs)` 逻辑：
  1. 尝试 `fetch(url, { method:'HEAD', signal })`，`resp.ok/status` 取 `resp.status`。
  2. 若抛错（超时/网络/HEAD 被拒返回 403/405 也算失败）→ 回退 `fetch(url, { method:'GET', headers:{ Range:'bytes=0-0' }, redirect:'follow', signal })`，成功取 `resp.status`。
  3. 仍失败 → 返回 `0`。
  4. `timeoutMs` 用命名常量 `const DEAD_URL_TIMEOUT = 5000`；每次回退前重置 `AbortController` 超时。
- 路由主体改为：
  1. 查询可见链接 `SELECT id, url FROM links WHERE is_visible = 1`。
  2. 用 `runWithConcurrency(links, 5, async link => ({ id: link.id, status: await detectUrl(link.url, DEAD_URL_TIMEOUT) }))` 收集结果。
  3. 返回 `res.json(results)`；keep `auth` 中间件。

> 说明：并发上限与超时用命名常量（非 UI 可配），避免过度设计。

### 2. 前端 REST 服务：无需改动
`src/services/rest/index.ts` 已透传后端结果，签名未变，不动。

### 3. 前端 Supabase 服务：修复可达性 + 并发
**文件**：`src/services/supabase/index.ts#L101-L124`

- 删除 `mode:'no-cors'` 下依赖 `resp.status` 的错误逻辑。
- 新增前端并发工具（页内小函数或文件内局部函数 `runWithConcurrency`）。
- 单链接检测改为以「请求是否可达」判定：
  ```ts
  async function detectUrlReachable(url: string, timeoutMs: number): Promise<number> {
    const controller = new AbortController()
    const t = setTimeout(() => controller.abort(), timeoutMs)
    try {
      await fetch(url, { method: 'GET', signal: controller.signal, mode: 'no-cors', cache: 'no-store' })
      // no-cors 下无法读真实状态：请求建立且未抛错即视为可达，返回 200
      return 200
    } catch {
      return 0 // 超时/网络错误/DNS 失败 → 死链
    } finally {
      clearTimeout(t)
    }
  }
  ```
  - `checkDeadLinks()` 内：查询可见链接后，用并发执行器（limit 5）批量检测，返回 `{id, status}[]`。
- 效果：修复「所有链接被判死」的问题，Supabase 模式能正确区分死链（不可达）与存活（可达）。

## 假设与决策 Assumptions & Decisions

- **运行模式**：以 REST 后端作为完整状态检测基准；Supabase 模式以「可达性」兜底（因 serverless 环境下无服务端代理，`no-cors` 下无法读取真实 HTTP 状态码）。两者都做并发 + 回退改进。
- **绩效参数**：并发上限 `5`、单链接超时 `5000ms`，以命名常量内联，不做 UI 配置。
- **检测范围**：沿用现状只检测 `is_visible = 1` 的可见链接。
- **状态码语义**：`status===0`（不可达）或 `status>=400` 视为失效；其余视为存活。
- **不动契约/后端 schema**：不新增数据库字段、不改 `checkDeadLinks` 签名，降低改动面与风险。
- **Supabase 可达性语义**：`no-cors GET` 不抛错即判可达（status 记 200），抛错判死（status 记 0）。这是无服务端场景下能做到的最准确判定。
