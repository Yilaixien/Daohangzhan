# 后台登录失败排查方案（「用户名或密码错误」401）

## 一、摘要

用户反馈：本次上线「Neon 只读加速缓存层」后，后台登录提示**「用户名或密码错误」**，本地 dev 与线上部署**两个环境都失败**；期间**未改动数据库，也未改动 Makers 控制台环境变量**，仅重新构建部署了代码。

代码层排查已完成，结论：**本次改动未引入登录回归**。需转向运行时数据/连接侧定位，本方案给出最小化诊断与修复路径。

## 二、现状分析（已完成的核查）

| 核查项 | 结果 |
|---|---|
| `login` 校验逻辑 | [[[default]].js L320-344](file:///workspace/edge-functions/api/[[default]].js#L320-L344) 与改动前 `git diff` **逐行一致**：`SELECT ... WHERE key IN ('admin_user','admin_pwd')` → 用户名/空 hash 判断 → `pgcrypto.crypt` 校验 → JWT 签发；无任何改动 |
| `getRuntime` 拆分 | 原 `runtimeCache` 拆为 `sqlCache/secretCache`，逻辑等价；缺变量会抛 500「缺少环境变量」，不是 401 |
| 依赖版本 | lockfile 确认 jose 6.2.10、@neondatabase/serverless 1.1.0 **与改动前相同**；新增仅 @edgeone/pages-blob 0.0.16 |
| 前端登录链路 | [auth.ts](file:///workspace/src/stores/auth.ts#L22-L36) 与 `apiFetch` 的 401 分支未改动；「用户名或密码错误」文案即后端 `fail()` 原样返回 |
| 新增代码 | 快照/click 全部为只读或 Blob 写入；**没有任何代码会改写 config.admin_pwd**；`afterDataWrite` 对 POST /auth/login 显式排除 |
| 构建产物 | `npm run build` 通过，esbuild 内联正常（此前已验证产物含新逻辑） |

**「用户名或密码错误」401 仅可能来自 login 内三个条件之一：**
1. `username !== adminUser`（登录用户名与 `config.admin_user` 不匹配，默认 `admin`）；
2. `!adminPwdHash`（**`config.admin_pwd` 为空、被清空、或当前连接读不到该行**）；
3. `crypt(password, hash)` 校验不通过（输入密码与 hash 对应明文不符，或 **hash 格式损坏**（非 `$2a$/$2b$` 前缀/为空串）。

由于代码、依赖、env 未变，**根因必为条件 1/2/3 之一**。最常见诱因：
- `admin_pwd` 为空：可能某次初始化未完成 / 数据分支被切换 / RLS 把该行过滤（连接串误用低权限角色）；
- 密码记错或最近修改过；
- import `@edgeone/pages-blob` 若导致线上模块崩溃会整体 5xx，不会 401（已排除，用户能看到 401 即模块加载正常）。

## 三、诊断步骤（先取证，再修复）

### 步骤 1：数据库侧只读验证（最快、最关键）

在 **Neon 控制台 → SQL Editor**（用项目主角色）执行：

```sql
-- 1) admin_user / admin_pwd 是否存在、有无值、hash 前缀
SELECT key, value <> '' AS has_value, left(value, 7) AS prefix
FROM config
WHERE key IN ('admin_user', 'admin_pwd');

-- 2) 用你的登录明文密码直接验证 crypt（把 <你的密码> 替换为实际登录密码）
SELECT (replace(value, '$2b$', '$2a$') = crypt('<你的密码>', replace(value, '$2b$', '$2a$'))) AS ok
FROM config WHERE key = 'admin_pwd' LIMIT 1;
```

判读：
- 第 1 条：`admin_pwd` 行**不存在或 has_value=false** → 命中条件 2（数据库侧被清空）→ 走「修复 A：重置密码」；
- 第 1 条正常（`$2a$`/`$2b$` 前缀）但第 2 条 `ok=false` → 命中条件 3（密码不对或 hash 损坏）→ 走「修复 A」；
- 第 2 条 `ok=true` 却仍 401 → 问题在**部署连接**（函数连到的库≠你查的库）→ 走「修复 B：核对连接串/角色」。

### 步骤 2：本地复现并抓函数日志（确认部署链路）

```bash
edgeone makers link      # 若无本地 env：从控制台同步（含 DATABASE_URL_ADMIN / JWT_SECRET）
edgeone makers dev
# 另开终端
curl -i -X POST http://localhost:8088/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<你的密码>"}'
```
观察：
- 返回 401 + 「用户名或密码错误」→ 与线上一致，问题在数据侧（做步骤 1 即可定位）；
- 返回 500 / 缺少环境变量 → 本地 env 未配置或函数异常，属部署配置问题；
- 函数控制台如有 `snapshot_rebuild_error` / 545 等异常一并记录。

### 步骤 3：核对线上连接角色（若步骤 1 通过仍失败）

- 确认 Makers 控制台函数变量 `DATABASE_URL_ADMIN` 是 **nav_admin** 连接串（不是 nav_read/主角色）。nav_read 的 RLS 会把 `admin_pwd` 行过滤 → 条件 2 触发、且首页快照等看起来正常（快照查询本身不含 admin_pwd），与现象完全吻合；
- 确认 `JWT_SECRET` 已配置（缺失会 500，非 401，双保险确认）。

## 四、修复动作

### 修复 A：重置管理员密码（条件 2/3 时执行）

在 Neon SQL Editor（主角色）执行，**先生成新 bcrypt hash**：

```bash
node -e "console.log(require('bcryptjs').hashSync('<新强密码≥16位>', 10))"
```

再写入：

```sql
UPDATE config SET value='<上面生成的hash>' WHERE key='admin_pwd';
```

随后两个环境都用新密码登录校验通过后，本修复即完成。若希望顺手验证快照不含敏感信息：`GET /api/frontend-data` 的 `data.config` 不应出现 `admin_pwd` 键（现有 rebuild 已强制 `KEY <> 'admin_pwd'`）。

### 修复 B：连接/权限问题（步骤 3 命中时执行）

- 将 `DATABASE_URL_ADMIN` 改为 nav_admin 连接串（Makers 控制台 → 项目 → 环境变量 → 保存 → 重新部署）；
- 若 nav_admin 角色确实具备全部权限但仍读不到，检查 RLS 策略是否被改动（`SELECT * FROM pg_policies WHERE tablename='config'`）。

### 修复 C（可选加固，代码层，随本方案一起交付）

在 `login` 中增加**无泄露审计日志**，便于下次秒级定位（不输出 hash 明文）：

```js
// login 中 cfg 组装后追加
console.log(JSON.stringify({
  event: 'login_probe',
  username_input: username || '',
  admin_user_present: cfg.admin_user !== undefined,
  admin_pwd_empty: !cfg.admin_pwd,
  admin_pwd_prefix: cfg.admin_pwd ? cfg.admin_pwd.slice(0, 4) : '',
}))
```
- 不记录密码与完整 hash，仅记录存在性与前缀；
- 对「SQL 异常」路径保持抛错（500）不变，与「业务 401」区分，避免再出现『两环境一致却无日志可查』的盲区。

## 五、假设与决策

1. **假设**：登录失败的根因是运行时数据/连接，而非本次代码改动（已通过 diff/依赖/前端/打包四重核查排除代码回归）。
2. **决策**：采用「先取证后修复」，避免无凭据地猜改；诊断步骤均只读、无副作用。
3. **兜底**：若用户无法提供数据库访问（连接串或控制台），则将修复收敛为「修复 B 核对 + 修复 A 重置」二选一，按控制台可见信息推进。
4. 本方案不修改既有快照/点击统计功能；修复 A/B 不涉及代码。

## 六、验证步骤

1. `curl -i -X POST .../api/auth/login -d '{"username":"admin","password":"<新密码>"}'` → 返回 200 且 `{ data: { token } }`；
2. 浏览器登录后台 → 进入管理端（链接/分组/配置可查可改）；
3. 回归确认公开功能不受影响：`GET /api/frontend-data` 返回 200 且 `data.config` 无 `admin_pwd`；首页/关于/申请收录正常渲染；
4. （若采纳修复 C）控制台日志出现 `login_probe` 且仅含存在性/前缀信息。

## 七、执行顺序建议

1. 先跑「步骤 1」SQL（用户在其 Neon 控制台执行，约 1 分钟）——直接把根因锁定在条件 1/2/3 之内；
2. 按命中条件执行「修复 A」或「修复 B」；
3. 复查 401 消失、后台可用；
4. 决定是否一并合入「修复 C」审计日志。
